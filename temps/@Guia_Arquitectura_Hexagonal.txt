1. Introducción: El Problema de la Deuda Técnica y la 
Necesidad de Desacoplamiento 
 
1.1 El Escenario Clásico: El Monolito Acoplado 
En la industria del software, un patrón recurrente —especialmente en startups y proyectos 
heredados (legacy systems)— es la arquitectura monolítica fuertemente acoplada. En este modelo, 
la lógica de negocio, el acceso a datos, el enrutamiento HTTP y la interfaz de usuario conviven 
entrelazados en los mismos módulos o clases. El siguiente fragmento conceptual ilustra el 
problema: 
 
# ❌ ANTI-PATRÓN: Sistema de pagos monolítico acoplado 
from fastapi import FastAPI 
from sqlalchemy import create_engine 
 
app = FastAPI() 
engine = create_engine('postgresql://...') 
 
@app.post('/pago') 
def procesar_pago(monto: float, cliente_id: int): 
    # Regla de negocio mezclada con infraestructura 
    if monto <= 0: 
        raise ValueError('Monto inválido')       # Regla de negocio 
    # Acceso directo a DB desde el controlador HTTP 
    with engine.connect() as conn: 
        conn.execute('INSERT INTO pagos ...')    # Infraestructura 
    # Notificación mezclada con la transacción 
    requests.post('https://notify.io/...')       # Adaptador externo 
    return {'status': 'ok'} 
 
Este código, aunque funcional en su etapa inicial, genera las siguientes consecuencias a mediano 
y largo plazo: 
• Fragilidad ante el cambio: Modificar la regla 'monto <= 0' obliga a tocar el mismo archivo 
que maneja HTTP y SQL, incrementando el riesgo de regresiones. 
• Imposibilidad de pruebas unitarias: Para probar la validación del monto se necesita una 
base de datos real y un servidor HTTP activo. 
• Acoplamiento tecnológico: Migrar de PostgreSQL a MongoDB implica reescribir código 
que contiene reglas de negocio críticas. 
• Deuda técnica exponencial: A medida que el sistema crece, cada nueva funcionalidad 
agrega más dependencias cruzadas, degradando la mantenibilidad. 
 
1.2 ¿Por qué Arquitectura Hexagonal? 
La Arquitectura Hexagonal, también conocida como Ports & Adapters (Puertos y Adaptadores), fue 
formulada por Alistair Cockburn en 2005. Su premisa fundamental es: 
Idea en una frase (lenguaje sencillo): el corazón del sistema (dominio + casos de uso) no debe 
depender de la forma como llegan las solicitudes (HTTP, CLI, eventos) ni de cómo se guardan los

datos (PostgreSQL, MongoDB, archivos). Eso se logra usando 'puertos' (interfaces) y 'adaptadores' 
(implementaciones). 
 
Principio Fundacional 
"Permite que una aplicación sea dirigida igualmente por usuarios, programas, pruebas 
automatizadas o scripts batch, y que sea desarrollada y probada de forma aislada de sus 
eventuales dispositivos de ejecución y bases de datos." 
— Alistair Cockburn, 2005 
 
Es un subconjunto de la filosofía 'Clean Architecture' de Robert C. Martin, con una topología 
específica basada en la metáfora del hexágono. Sus objetivos estratégicos son: 
1. Mantenibilidad: El código de negocio es estable y evoluciona independientemente de la 
infraestructura. 
2. Modularidad: Componentes perfectamente delimitados que pueden ser reemplazados sin 
efecto dominó. 
3. Testabilidad: El núcleo puede ser probado en milisegundos sin base de datos, sin HTTP, 
sin servicios externos. 
4. Independencia tecnológica: La aplicación no queda 'casada' con ningún framework, ORM 
o base de datos específica. 
 
⚠️ La Regla de Oro 
Si la implementación de Arquitectura Hexagonal no resulta en un código más limpio, 
más modular y más fácil de probar, la implementación es incorrecta. 
Esta regla será el criterio primario de evaluación en el trabajo extra clase.

2. Anatomía de la Arquitectura: Diseccionando Cada 
Capa 
La metáfora del hexágono no impone exactamente seis lados; es una representación visual de un 
núcleo rodeado de interfaces. La arquitectura se compone de tres anillos concéntricos: el Dominio 
en el centro, la Aplicación en el intermedio, y los Adaptadores en el exterior. El siguiente diagrama 
textual ilustra la estructura: 
 
 
 
 
 
2.1 El Dominio: El Núcleo Soberano 
Definición y responsabilidad: El dominio es el corazón de la aplicación. Contiene el conocimiento 
que pertenece exclusivamente al negocio: sus reglas, sus invariantes y sus conceptos. Es 
completamente agnóstico al exterior: desconoce la existencia de bases de datos, frameworks web, 
servicios externos, colas de mensajes o cualquier detalle técnico. 
 
Composición del dominio: 
• Entidades (Entities): Objetos con identidad propia que persisten en el tiempo. Ejemplo: 
Cliente, Transaccion, Pedido. Encapsulan estado y comportamiento de negocio. 
• Objetos de Valor (Value Objects): Objetos inmutables definidos por sus atributos, sin 
identidad propia. Ejemplo: Dinero(monto=100, moneda='COP'), Direccion, Email.

• Agregados (Aggregates): Cluster de entidades y objetos de valor tratados como una 
unidad transaccional. Ejemplo: un Pedido con sus ItemsDePedido. 
• Eventos de Dominio (Domain Events): Registros inmutables de algo que ocurrió. 
Ejemplo: PagoAprobado, ClienteCreado. Son cruciales para arquitecturas orientadas a 
eventos. 
• Excepciones de Dominio: Errores que representan violaciones de reglas de negocio. 
Ejemplo: SaldoInsuficienteError, LimiteTransaccionExcedidoError. 
 
Implementación en Python con Pydantic: 
La elección de Pydantic para el dominio es estratégica: permite definir modelos con validación de 
tipos estricta sin introducir dependencias de infraestructura como SQLAlchemy o Django ORM. 
 
# dominio/entidades.py 
from pydantic import BaseModel, field_validator, model_validator 
from uuid import UUID, uuid4 
from decimal import Decimal 
from datetime import datetime 
from enum import Enum 
 
class EstadoTransaccion(Enum): 
    PENDIENTE = 'PENDIENTE' 
    APROBADA  = 'APROBADA' 
    RECHAZADA = 'RECHAZADA' 
 
class Dinero(BaseModel):  # Objeto de Valor 
    monto: Decimal 
    moneda: str = 'COP' 
 
    @field_validator('monto') 
    @classmethod 
    def monto_positivo(cls, v): 
        if v <= 0: 
            raise ValueError('El monto debe ser mayor a cero') 
        return v 
 
    def __add__(self, otro: 'Dinero') -> 'Dinero': 
        if self.moneda != otro.moneda: 
            raise ValueError('No se pueden sumar monedas distintas') 
        return Dinero(monto=self.monto + otro.monto, moneda=self.moneda) 
 
class Transaccion(BaseModel):  # Entidad 
    id: UUID = uuid4() 
    cliente_id: UUID 
    valor: Dinero 
    estado: EstadoTransaccion = EstadoTransaccion.PENDIENTE 
    creada_en: datetime = datetime.utcnow() 
 
    def aprobar(self) -> None: 
        '''Regla de negocio: solo se puede aprobar si está pendiente''' 
        if self.estado != EstadoTransaccion.PENDIENTE:

⚠️ Error Crítico — Violación del Dominio 
NUNCA incluya imports de librerías de infraestructura en el dominio: 
from sqlalchemy import Column  # ❌ VIOLA la arquitectura 
from fastapi import Request     # ❌ VIOLA la arquitectura 
import requests                  # ❌ VIOLA la arquitectura 
El único import externo permitido en el dominio es Pydantic y las librerías estándar de 
Python. 
 
2.2 Los Puertos: El Contrato entre el Núcleo y el Exterior 
Definición: Los puertos son interfaces abstractas —contratos estrictos— que definen cómo el 
mundo exterior puede interactuar con el dominio y cómo el dominio puede solicitar servicios al 
exterior. No son clases concretas; son especificaciones de comportamiento. 
En Python se implementan mediante dos mecanismos: 
• abc.ABC con @abstractmethod: Para contratos formales con herencia explícita. 
• typing.Protocol: Para contratos estructurales (duck typing). Más flexible y no requiere 
herencia. 
 
2.2.1 Puertos de Entrada (Input Ports) 
Propósito: Definen cómo el mundo exterior "habla" con la aplicación. Son la "Definición de Uso": 
especifican qué acciones están disponibles para los actores externos.

2.3 La Capa de Aplicación: Los Casos de Uso 
Definición: La capa de aplicación contiene los Casos de Uso (Use Cases): orquestadores que 
coordinan el flujo entre el Puerto de Entrada, las entidades del Dominio y el Puerto de Salida. 
Preferimos el término 'Caso de Uso' sobre 'Servicio' porque expresa la intención del negocio, no un 
rol técnico. 
Responsabilidades del Caso de Uso: 
5. Recibir el comando/query desde el Puerto de Entrada. 
6. Validar pre-condiciones de orquestación (no de dominio). 
7. Invocar las reglas de negocio en las entidades del Dominio. 
8. Utilizar los Puertos de Salida para persistir o comunicar. 
9. Retornar el resultado al Puerto de Entrada. 
 
# aplicacion/casos_de_uso.py

from decimal import Decimal

2.4 Los Adaptadores: La Conexión con el Mundo Real 
Definición: Los adaptadores son las implementaciones concretas de los puertos. Son el único 
lugar donde se mencionan tecnologías específicas como FastAPI, SQLAlchemy, Kafka o AWS S3. 
Existen dos tipos: 
 
2.4.1 Adaptadores de Entrada (Driving / Primary Adapters) 
Son los actores que inician la interacción con la aplicación. Su único trabajo es traducir el

# adaptadores/entrada/api_rest.py 
from fastapi import APIRouter, Depends, HTTPException 
from pydantic import BaseModel 
from uuid import UUID 
from puertos.entrada import ServicioTransaccionesPort, ComandoCrearTransaccion 
 
router = APIRouter(prefix='/transacciones', tags=['Transacciones']) 
 
class CrearTransaccionRequest(BaseModel):  # DTO de entrada HTTP 
    cliente_id: UUID 
    monto: float 
    moneda: str = 'COP' 
 
class TransaccionResponse(BaseModel):       # DTO de salida HTTP 
    id: str 
    estado: str 
    monto: float 
 
def get_servicio() -> ServicioTransaccionesPort: 
    from config.contenedor import contenedor  # Inyección de dependencias 
    return contenedor.servicio_transacciones 
 
@router.post('/', response_model=TransaccionResponse) 
def crear_transaccion( 
    request: CrearTransaccionRequest, 
    servicio: ServicioTransaccionesPort = Depends(get_servicio) 
): 
    '''El controlador NO tiene lógica de negocio. Solo traduce HTTP → Puerto''' 
    comando = ComandoCrearTransaccion( 
        cliente_id=request.cliente_id, 
        monto=request.monto, 
        moneda=request.moneda 
    ) 
    try: 
        transaccion = servicio.crear_transaccion(comando) 
        return TransaccionResponse( 
            id=str(transaccion.id), 
            estado=transaccion.estado.value, 
            monto=float(transaccion.valor.monto) 
        ) 
    except ValueError as e: 
        raise HTTPException(status_code=400, detail=str(e))

    cliente_id = Column(String, nullable=False)

class RepositorioTransaccionPostgres(TransaccionRepositorioPort): 
    '''Adaptador de Salida: implementa el puerto con PostgreSQL + SQLAlchemy''' 
 
    def __init__(self, session: Session): 
        self._session = session 
 
    def guardar(self, transaccion: Transaccion) -> None: 
        orm = TransaccionORM( 
            id=str(transaccion.id), 
            cliente_id=str(transaccion.cliente_id), 
            monto=transaccion.valor.monto, 
            moneda=transaccion.valor.moneda, 
            estado=transaccion.estado 
        ) 
        self._session.merge(orm) 
        self._session.commit() 
 
    def buscar_por_id(self, transaccion_id: UUID) -> Transaccion | None: 
        orm = self._session.get(TransaccionORM, str(transaccion_id)) 
        if orm is None: 
            return None 
        return Transaccion( 
            id=UUID(orm.id), 
            cliente_id=UUID(orm.cliente_id), 
            valor=Dinero(monto=Decimal(str(orm.monto)), moneda=orm.moneda), 
            estado=orm.estado 
        ) 
 
2.5 La Regla de Dependencia: El Principio más Importante 
Definición: La Regla de Dependencia establece que las dependencias a nivel de código fuente 
deben apuntar exclusivamente hacia el interior —hacia el dominio. Esta regla es inviolable y es el 
mecanismo que garantiza el desacoplamiento. 
 
Regla de Dependencia — Resumen Visual

PERMITIDO:  Adaptador → Puerto → Caso de Uso → Dominio 
PROHIBIDO:  Dominio → Puerto   (el dominio no conoce los puertos) 
PROHIBIDO:  Dominio → Adaptador (el dominio nunca conoce la 
infraestructura) 
PROHIBIDO:  Caso de Uso → Adaptador concreto (solo conoce el puerto 
abstracto) 
 
La 'magia' que permite que el flujo de control vaya de izquierda a derecha (FastAPI → Caso de 
Uso → PostgreSQL) mientras las dependencias de código apuntan hacia el centro, se llama 
Inversión de Dependencias (Dependency Inversion Principle — DIP). El Caso de Uso depende de 
la abstracción (el puerto), no de la implementación concreta. En tiempo de ejecución, la 
implementación concreta se inyecta externamente (contenedor de inyección de dependencias).

4. Estrategia de Pruebas: La Pirámide de Testing 
Una de las mayores ventajas de la Arquitectura Hexagonal es que habilita una pirámide de pruebas 
eficiente: muchas pruebas unitarias rápidas, pocas pruebas de integración medianas, y mínimas 
pruebas end-to-end costosas. 
 
 
La Arquitectura Hexagonal hace posible la Pirámide de Testing porque aísla el código que cambia 
con frecuencia y es fácil de probar (el Dominio/Centro) del código que es rígido, lento y difícil de 
probar (la Infraestructura/Bordes). 
 
A continuación la explicación de cómo se mapea cada nivel de la pirámide con las capas del 
hexágono: 
 
1. La Base: Pruebas Unitarias y el Dominio Puro 
• En la Pirámide: Representa la base amplia. Son pruebas muy rápidas (milisegundos), 
masivas en cantidad y, preferiblemente, sin mocks (simulaciones). 
• En el Hexágono: Corresponde a la Capa de Dominio (Entidades, Objetos de Valor, 
Reglas de negocio) y gran parte de la Capa de Aplicación (Casos de Uso). 
• Por qué encajan: Como la regla de oro de la Arquitectura Hexagonal dicta que el Dominio 
tiene cero dependencias externas, puedes instanciar tus clases de dominio y probar toda 
tu lógica de negocio en memoria pura. No necesitas levantar una base de datos ni un 
servidor web. Si un Caso de Uso necesita interactuar con el exterior, simplemente le 
inyectas una implementación "Falsa" (Fake) o un Mock del Puerto de Salida, manteniendo 
la prueba ultrarrápida.

2. El Medio: Pruebas de Integración y los Adaptadores 
• En la Pirámide: Representa el nivel intermedio. Son menos pruebas que las unitarias, 
toman un poco más de tiempo y suelen usar adaptadores en memoria (como bases de 
datos H2 o SQLite) o contenedores ligeros. 
• En el Hexágono: Corresponde a la Capa de Infraestructura, específicamente probando 
los Adaptadores de forma aislada para asegurar que implementan correctamente los 
Puertos. 
• Por qué encajan: Aquí es donde verificas que tu código de SQLAlchemy realmente guarda 
y recupera datos de la base de datos, o que tu router de FastAPI responde con los códigos 
HTTP correctos. Pruebas que el exterior del hexágono se comunica bien con tus interfaces 
(Puertos), sin necesidad de probar toda la lógica de negocio (que ya está cubierta en la 
base). 
3. La Cúspide: Pruebas E2E (End-to-End) y el Sistema Completo 
• En la Pirámide: Es la punta. Son muy pocas pruebas porque son lentas, frágiles y costosas 
de mantener. Requieren levantar el entorno completo (Docker, DB real, HTTP). 
• En el Hexágono: Es una petición que atraviesa absolutamente todas las capas: Entra 
por el Adaptador Driving (FastAPI), cruza el Puerto de Entrada, ejecuta el Caso de Uso 
(Aplicación), altera el Dominio, sale por el Puerto de Salida y persiste en el Adaptador 
Driven (SQLAlchemy/PostgreSQL). 
• Por qué encajan: En la Arquitectura Hexagonal, el E2E se usa solo como una prueba de 
humo (smoke test) para garantizar que el ensamblaje de todas las piezas (la inyección de 
dependencias y la configuración del framework) funciona correctamente en un entorno 
similar a producción. No se usan para probar reglas de negocio.

5. Evolución de la Aplicación Apoyada en la 
Arquitectura Hexagonal 
Cómo evolucionar una aplicación con arquitectura hexagonal (guía práctica): 
1) Cambios por 'canal' (entradas): si aparece un nuevo canal (WhatsApp, CLI, batch, eventos), 
crea un adaptador de entrada nuevo. El núcleo no cambia. 
2) Cambios por 'tecnología' (salidas): si cambia la base de datos, el proveedor de correo o un API 
externo, crea un adaptador de salida nuevo que implemente el mismo puerto. 
3) Cambios por 'regla de negocio' (dominio): si cambia una regla (por ejemplo, la multa, límites, 
estados), cambia solo el dominio y ajusta pruebas unitarias; los adaptadores deberían requerir 
pocos o cero cambios. 
4) Cambios por 'flujo' (casos de uso): si aparece un caso de uso nuevo (por ejemplo 'reservar 
libro'), normalmente agregas un puerto de entrada + un caso de uso; el dominio puede reutilizar 
entidades existentes. 
Tip para estudiantes: cuando hagas un cambio, intenta responder: ¿este cambio es de negocio, de 
canal o de tecnología? Esa respuesta te dice en qué carpeta debería vivir el cambio. 
Una de las promesas más poderosas de la Arquitectura Hexagonal es que el sistema puede 
crecer, escalar y transformarse radicalmente sin tocar el núcleo de negocio. A continuación se 
detallan los escenarios de evolución más comunes:

# adaptadores/salida/repositorio_mongodb.py — NUEVO adaptador 
from pymongo import MongoClient 
from puertos.salida import TransaccionRepositorioPort 
from dominio.entidades import Transaccion, Dinero, EstadoTransaccion 
from uuid import UUID 
from decimal import Decimal 
 
class RepositorioTransaccionMongoDB(TransaccionRepositorioPort): 
    def __init__(self, uri: str, db: str): 
        self._col = MongoClient(uri)[db]['transacciones'] 
 
    def guardar(self, t: Transaccion) -> None: 
        self._col.update_one( 
            {'_id': str(t.id)}, 
            {'$set': {'cliente_id': str(t.cliente_id), 'monto': 
float(t.valor.monto), 
                      'moneda': t.valor.moneda, 'estado': t.estado.value}}, 
            upsert=True 
        ) 
 
    def buscar_por_id(self, id: UUID) -> Transaccion | None: 
        doc = self._col.find_one({'_id': str(id)}) 
        if not doc: return None 
        return Transaccion( 
            id=UUID(doc['_id']), 
            cliente_id=UUID(doc['cliente_id']), 
            valor=Dinero(monto=Decimal(str(doc['monto'])), moneda=doc['moneda']), 
            estado=EstadoTransaccion(doc['estado']) 
        )

5.3 Evolución 3: Transición a Arquitectura de Microservicios 
Escenario: La empresa crece y decide separar el sistema monolítico en microservicios. El módulo 
de pagos se convierte en su propio servicio independiente. 
La Arquitectura Hexagonal facilita enormemente esta transición porque las fronteras ya están 
definidas. Cada futuro microservicio ya existe como un conjunto coherente de capas. El proceso 
es: 
10. Identificar el Contexto Delimitado (Bounded Context): Pagos, Clientes, Notificaciones 
son candidatos naturales. 
11. Extraer el módulo: La carpeta dominio/, puertos/, aplicacion/ y adaptadores/ del contexto 
se mueven a un nuevo repositorio. 
12. Agregar comunicación entre servicios: Se crea un nuevo Adaptador de Salida que 
publica eventos en un Message Broker (Kafka, RabbitMQ) en lugar de llamar directamente 
al otro servicio.

import json

from puertos.salida import NotificadorPort 
from dominio.entidades import Transaccion

class PublicadorEventosKafka(NotificadorPort):

        self._producer = KafkaProducer(bootstrap_servers=bootstrap_servers, 
                                        value_serializer=lambda v:

        self._producer.send('pagos.aprobados', evento.dict()) 
        self._producer.flush()

6.2 Diagrama de Puertos y Adaptadores (Vista Hexagonal) 
Diagrama obligatorio que muestra explícitamente la estructura hexagonal del componente principal: 
 
 
 
1. Driving Side (Lado Izquierdo - Adaptadores de Entrada) 
Esta es la zona que "conduce" o inicia las acciones en la aplicación. 
• Adaptadores (Adapters IN): Son los puntos de contacto con el mundo exterior. El 
diagrama muestra que un sistema puede ser impulsado por múltiples mecanismos

• Su función: Traducir los datos específicos de su tecnología (un JSON HTTP, un argumento 
de consola, o un payload de RabbitMQ) a una estructura limpia y pasarlos al hexágono a 
través de un Puerto de Entrada.

Es el corazón inmutable del software, completamente aislado de frameworks externos. 
• Input Port (Puerto de Entrada): Definido típicamente en Python usando Clases Base 
Abstractas (ABC), expone las operaciones que el sistema puede realizar, actuando como 
una barrera protectora. 
• Caso de Uso (Use Case): Contiene la lógica de aplicación. Orquesta las acciones, recibe 
comandos de los puertos de entrada, interactúa con el dominio y delega la persistencia o 
notificaciones a los puertos de salida.

importar cómo se implemente. 
3. Driven Side (Lado Derecho - Adaptadores de Salida) 
Esta es la infraestructura que la aplicación "conduce" o controla para realizar efectos secundarios. 
• Adaptadores (Adapters OUT): Reciben las instrucciones del núcleo (a través de los 
Output Ports) y las traducen al lenguaje específico de la infraestructura. 
• Ejemplos: El diagrama ilustra adaptadores para interactuar con una base de datos 
(PostgreSQL Adapter), un bus de eventos (Kafka Adapter) y un servicio de correo (Email 
Adapter). 
4. La Regla de Oro: Inversión de Dependencias (DIP) 
El texto en la parte inferior del diagrama resalta el concepto más crítico para que esta arquitectura 
funcione: "Las flechas del lado derecho SALEN del núcleo pero las dependencias de CÓDIGO 
apuntan hacia adentro (el adaptador implementa el puerto, no al revés)". 
• Flujo de Control vs. Flujo de Dependencias: Aunque durante la ejecución del programa 
el Caso de Uso llama a la base de datos (las flechas horizontales apuntan de izquierda a 
derecha), a nivel de código fuente, el Caso de Uso solo importa y conoce la interfaz 
abstracta (Output Port). Es el PostgreSQL Adapter el que debe importar esa interfaz para 
implementarla, apuntando su dependencia hacia el centro. 
 
Esta separación estricta es lo que permite que el núcleo del sistema sea testeable de forma rápida 
(mediante pruebas unitarias) sin necesidad de levantar bases de datos ni servicios web, tal como lo 
vimos previamente en la Pirámide de Testing.

7.1 Descripción General 
Este trabajo aborda un escenario real: la mayor parte del trabajo de un ingeniero de software no 
consiste en diseñar sistemas desde cero, sino en evolucionar sistemas existentes que acumularon 
deuda técnica. El objetivo es tomar un sistema monolítico acoplado, refactorizarlo aplicando 
Arquitectura Hexagonal, y demostrar que la nueva arquitectura soporta una evolución que sería 
imposible (o extremadamente costosa) en el monolito original. 
 
Punto de partida: Proyecto previo de los estudiantes desarrollado como un monolítico de 
referencia.

11. Nota Final del Docente 
 
Mensaje para los Estudiantes 
La Arquitectura Hexagonal no es un fin en sí mismo. Es una herramienta que, cuando se 
aplica con criterio, produce sistemas que sobreviven al tiempo y a los cambios de 
requisitos. En el mercado laboral, la capacidad de razonar sobre fronteras arquitectónicas y 
de desacoplar responsabilidades es una de las habilidades más valoradas y menos 
comunes. 
 
Durante el desarrollo de estos trabajos, se enfrentarán a momentos donde la tentación de 
'tomar el atajo' —poner la lógica directamente en el controlador, o hacer que el dominio 
importe SQLAlchemy— será muy grande. Resístanla. Ese es exactamente el momento 
donde se aprende. 
 
El criterio de evaluación más importante no es que el código funcione, sino que 
funcione de la manera correcta. Un sistema que funciona pero con una arquitectura 
acoplada es simplemente deuda técnica aplazada. 
 
Se les desea mucho éxito en el proceso. Las preguntas son bienvenidas durante todo el 
desarrollo del trabajo.
